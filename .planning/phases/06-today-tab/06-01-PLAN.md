    export 하는 것:
    - `type RowChange<Row> = { event: "INSERT" | "UPDATE"; row: Row } | { event: "DELETE"; key: string | null }`
    - `type RowSetState<Row> = { rows: Row[]; loaded: boolean; error: string | null; pending: RowChange<Row>[] }`
    - `type RowSetAction<Row> = { type: "fetched"; rows: Row[] | null; error: { message: string } | null } | { type: "changed"; event: "INSERT" | "UPDATE"; row: Row } | { type: "changed"; event: "DELETE"; key: string | null }`
    - `initialRowSetState<Row>(): RowSetState<Row>` — 인스턴스마다 새 객체를 만든다(모듈 상수 하나를 공유하면 제네릭 인자가 갈린다).
    - `createRowSetReducer<Row>(keyOf: (row: Row) => string): (state: RowSetState<Row>, action: RowSetAction<Row>) => RowSetState<Row>`

    규칙(전부 `lib/restaurants.ts` 의 현행 동작을 옮긴 것이고 **한 가지만 다르다 — UPDATE 가 upsert 다**):
    - 모듈 내부 `applyChange(rows, change, keyOf)`: DELETE 는 `key === null` 이면 그대로, 아니면 그 키를 걸러 낸다. INSERT 는 같은 키가 이미 있으면 `rows` 를 그대로 돌려준다(멱등). UPDATE 는 같은 키가 있으면 통째로 교체하고 **없으면 끝에 추가한다**(upsert, D-05) — 얕은 병합은 하지 않는다.
    - `fetched`: `state.loaded` 가 참이면 `state` 를 그대로 돌려준다(중복 응답). **`error` 가 있으면 `rows` 가 함께 와도 실패 경로**다 — `{ rows: [], loaded: true, error: error.message, pending: [] }`. 없으면 `{ rows: state.pending.reduce(…, action.rows ?? []), loaded: true, error: null, pending: [] }` 로 버퍼를 **도착 순서대로** 재적용한다.
    - `changed`: `!state.loaded` 면 적용하지 않고 `pending` 에 쌓는다(여기서 `loaded` 를 올리지 않는 것이 CR-01 수정의 핵심이다). 로드 후에는 `error` 를 그대로 둔 채 행만 병합한다 — 이벤트 하나가 도착했다는 사실이 목록 전체를 읽을 수 있다는 증거는 아니다.
